# 세션 운영 규약

이 저장소에서 동시에 도는 세션들이 서로를 깨뜨리지 않기 위한 규칙.
**작업을 시작하기 전에 읽고, 그대로 따른다.**

2026-09-30 현재 네 개의 세션이 이 저장소를 함께 쓴다. 이름은 바뀔 수 있고,
역할도 겹칠 수 있다. 아래 규칙은 누가 무엇을 하든 동일하게 적용된다.

---

## 왜 이 문서가 있는가

2026-09-30, 두 세션이 같은 날 `src/rlwrld_worklog/cli.py` 를 서로 모르고
고쳤다. 한쪽이 옛 기준으로 고쳐 main 에 직접 커밋했고, 그 커밋이 다른 쪽의
변경을 되돌렸다. 테스트 두 개가 빨개져 패치 큐가 멈췄고 배포도 함께 섰다.
**26분 동안 아무도 몰랐다.** 발견은 사람이 같은 명령을 다시 돌려 출력이
예전으로 돌아간 것을 눈치챘기 때문이다.

두 세션 다 잘못한 것이 없다. 서로가 무엇을 만지는지 볼 방법이 없었을 뿐이다.

이후 최근 패치 26건을 실제로 세어 보았다:

* 패치 캐리어(`incoming/`)를 통과한 작업들 — **충돌 0건.** 한 번에 하나씩
  적용되고, 테스트를 통과해야 푸시되기 때문이다.
* 캐리어를 거치지 않고 main 에 직접 들어온 작업 — **사고 1건, 30분.**

규칙은 그래서 하나로 줄어든다.

---

## 규칙

### 1. main 을 체크아웃하고 작업하지 않는다

세션마다 자기 브랜치에서 일한다. 브랜치 이름은 세션이 하는 일로:

```bash
git switch -c bookmarks/internal-links
git switch -c roadmap/db-backed
git switch -c gpu/pricing-page
```

`git branch` 한 줄이면 지금 누가 무엇을 물고 있는지 보인다. 이것 하나로
2026-09-30 의 사고는 일어나지 않는다.

**작업 전에 확인할 것:**

```bash
git branch -v          # 다른 세션이 무엇을 물고 있나
git status --short     # 트리가 깨끗한가 (아니면 남의 작업이 올라와 있다)
```

트리가 더럽고 그게 내 작업이 아니면 **건드리지 않는다.** `git stash`,
`git checkout --`, `git reset` 전부 남의 30분을 지울 수 있다. 사람에게
말하고 멈춘다.

### 2. 시작하기 전에 `git fetch` 한다

```bash
git fetch origin && git log --oneline -5 origin/main
```

2026-09-30 의 사고에서 내 쪽 잘못은 이것이었다. 나는 `origin/main` 보다 **10
커밋 뒤처진 상태**에서 패치를 만들고 있었고, 그 사실을 알아챌 방법은 이 한
줄뿐이었는데 돌리지 않았다. 낡은 기준 위에서 만든 변경은 남의 작업을 되돌린다
— 방향이 어느 쪽이든.

작업 도중에도 오래 걸리는 일이면 다시 한 번 확인한다.

### 3. main 에 올라가는 길은 하나뿐이다

**푸시 전에 이 기계에서 전체 테스트가 초록이어야 한다.** 테스트를 통과하지
않은 코드가 main 에 올라가면 다른 세션 전부가 그 위에서 일하게 된다.

경로는 둘 중 하나다:

* **패치 캐리어** — 커밋하고 `git format-patch -1 -o incoming/` 후 손을 뗀다.
  3 분 안에 캐리어가 하나씩 순서대로 적용하고, 전체 테스트를 돌리고, 초록일
  때만 푸시하고, 결과를 `incoming/last-run.json` 에 남긴다. 실패한 패치는
  `incoming/failed/`, 성공한 것은 `incoming/applied/` 로 간다.
* **직접 푸시** — 자기 브랜치를 GitHub 에 푸시한다. 이 경우 테스트는 아무도
  대신 돌려주지 않으므로 **푸시 전에 직접 돌린다.**

어느 쪽이든 `origin/main` 에 들어간 것은 30 분 안에 통합데브가 다시 검증한다
(아래).

### 4. 통합데브가 origin/main 을 다시 검증한다

`hkwa-integration.timer` 가 30 분마다 `origin/main` 을 별도 클론으로 풀 받아,
별도 데이터베이스(`worklog_dev`) 상대로 전체 테스트를 돌리고 결과를
`incoming/last-integration.json` 에 남긴다.

```bash
cat incoming/last-integration.json
```

`outcome` 이 `green` 이면 그 커밋은 이 기계에서 실제로 돈다. `red` 면 어느
테스트인지 적혀 있다. **고치지도 되돌리지도 않는다** — 사실만 남긴다.

이 층이 있는 이유: 캐리어는 자기를 통과한 것만 테스트한다. 직접 커밋하거나
직접 푸시한 변경은 캐리어를 거치지 않으므로, 관문이 그쪽에만 있으면 사실상
관문이 없다.

데이터베이스가 따로인 것도 같은 이유다. 테스트는 원장 행을 만들고 지운다 —
운영 DB 를 가리키면 테스트 하나가 밤새 수집한 것을 지울 수 있다.

### 5. 착수할 때 보드에 올린다

일을 시작할 때 보드 항목을 만들거나 이미 있는 항목을 `in_progress` 로
옮긴다. 끝나고 올리는 것이 아니다 — 끝나고 올린 일은 아무도 방향을 바꿔줄
수 없었던 일이다.

커밋 메시지에 항목 번호를 적는다:

```
Refs wi_1bda10e6938ed059
```

캐리어가 이것을 읽어 `incoming/last-run.json` 의 `items` 에 남긴다. 비어
있으면 보드에 없는 작업이 들어왔다는 뜻이고, 그건 질문거리가 된다.
**막지는 않는다.** 일에 대한 메모를 강제하려고 일을 세우지 않는다.

### 6. "고쳤는데 그대로" 면 코드를 파기 전에 `last-run.json` 을 읽는다

```bash
cat incoming/last-run.json
```

이 파일이 답을 갖고 있는 경우가 실제로 여러 번 있었다:

* `refused` — 트리가 더러워 캐리어가 멈춰 있다. 어느 파일 때문인지, 몇 분째
  인지 적혀 있다.
* `apply-failed` — 패치가 `incoming/failed/` 에 있다.
* `tests-failed` — 적용은 됐지만 초록이 아니라 푸시가 안 됐다.
* `idle` / `pushed` — 캐리어는 할 일을 했다. 문제는 다른 데 있다.

배포 상태는 `incoming/last-deploy.json` 이 따로 말해준다. **커밋된 코드와
지금 돌고 있는 코드는 다를 수 있다.**

### 7. 내가 하지 않은 작업을 덮지 않는다

남의 커밋을 리베이스하거나, 남의 브랜치를 고치거나, 남의 미완성 작업을
정리하지 않는다. 어떻게 할지는 사람이 정한다.

남의 변경이 내 것을 되돌렸을 때도 마찬가지다. 그들의 커밋을 고쳐 쓰는 대신,
**현재 파일 위에 내 변경만 다시 올린 패치**를 만든다. 리베이스는 여기서
923 줄을 날릴 수 있는 유일한 동작이다.

---

## 세션 종류가 달라도 규칙은 같다

조사·협상·문서 작업처럼 코드가 결과물이 아닌 세션도 있다. 그런 일의
결과물은 보드 항목이나 프로젝트 문서로 남긴다. 나중에 화면이나 수집기를
만들게 되면 그때는 위 규칙이 그대로 적용된다 — 예외를 두지 않는다.

## 요약

| | |
| --- | --- |
| 작업 시작 전 | `git fetch origin` — 뒤처진 채로 고치면 남의 것을 되돌린다 |
| main 에서 작업 | **안 한다.** 자기 브랜치에서 |
| main 에 올리기 | 캐리어(`incoming/`)에 맡기거나, 직접 푸시하되 **테스트를 먼저 돌린다** |
| 초록인지 확인 | `incoming/last-integration.json` |
| 착수 시 | 보드 항목 만들고, 커밋에 `Refs wi_...` |
| 안 고쳐질 때 | `incoming/last-run.json` 먼저 |
| 남의 변경 | 덮지 않는다. 사람에게 말한다 |
